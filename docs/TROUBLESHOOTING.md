## 1. LCD 背光亮但无显示

**现象**：给 LCD 通电后背光是亮的（说明供电正常），但屏幕上什么都没有，或者只有一排黑方块。

**排查顺序（按概率从高到低）：**

### 1.1 对比度电位器没调 ⭐ 最常见

I2C 转接板上有一颗**蓝色的小电位器**（可调电阻），它控制 LCD 的 V0 对比度引脚。

- **解决**：用十字螺丝刀**非常缓慢地**来回旋转，通常需要转十几圈才能找到合适位置，字符会逐渐浮现
- **原理**：LCD 的对比度决定了液晶分子的偏转角度对光线的调制程度。对比度过低 → 字符和背景一样亮（看不见）；过高 → 全部像素变黑（一排方块）

### 1.2 I2C 地址不对

模块出厂地址因芯片型号而异：

| 地址 | 芯片 |
| --- | --- |
| `0x27` | PCF8574T |
| `0x3F` | PCF8574AT |

- **解决**：先跑 [I2C 扫描程序](WIRING.md#3-i2c-地址扫描必做第一步)，把扫到的地址填进代码：

```cpp
LiquidCrystal_I2C lcd(0x27, 16, 2);   // ← 改成扫到的地址
```

- **原理**：I2C 总线上有多个设备时靠地址区分。地址写错，Arduino 发的数据没有设备应答，屏幕自然不动。

### 1.3 SDA/SCL 插错位置

- **解决**：Uno 上 I2C **必须是 A4（SDA）和 A5（SCL）**，插到 D4/D5 是不通的
- **注意**：其它板子不同（Nano 同为 A4/A5，Mega2560 是 D20/D21），换板要重新确认

### 1.4 转接板虚焊

自己焊的 I2C 转接板，16 个排针只要有一根没焊透，整屏就不显示。

- **解决**：万用表通断档逐针测量，或直接补焊一遍（尤其是 GND 和 VCC）
- **经验**：这个问题排查起来最费时间，因为它表现为「代码完全正确但不工作」。焊接后**先用万用表确认再插板**能省下大量时间。

### 1.5 库的 API 不兼容

不同版本的 `LiquidCrystal_I2C` 库初始化函数名不同：

```cpp
lcd.init();        // 本项目使用的版本（v1.1.2）
lcd.begin(16, 2);  // 部分其它版本
```

- **解决**：本项目已把可用的库版本打包在 [libraries/LiquidCrystal_I2C](../libraries/LiquidCrystal_I2C)，直接使用即可
- **原理**：`LiquidCrystal_I2C` 是社区维护库，历史上存在多个不兼容分支。用错版本编译能过但屏幕不动。

## 2. 手机发指令收到 FFFF / C7 乱码

**现象**：手机发送 `1`，电脑串口监视器打印 `BT Received (HEX): FFFF` 或 `C7`、`80` 之类的乱码，LCD 和 LED 完全无响应。

**这是本项目最经典的坑，两个原因，按顺序排查：**

### 2.1 波特率不匹配 ⭐ 最常见

你的 HC-05 出厂波特率可能不是代码里写的值。

| 代码里写的 | 模块实际 | 结果 |
| --- | --- | --- |
| `38400` | `9600` | ❌ 乱码 |
| `9600` | `38400` | ❌ 乱码 |

- **解决**：把代码改成你的模块实际波特率

```cpp
BT.begin(38400);   // 本项目实测值
// BT.begin(9600); // 如果你的模块是 9600 就改成这行
```

- **如何确定真实波特率**？依次试 `9600` / `19200` / `38400` / `57600` / `115200`，哪个能正确打印 `31`（即字符 `1`）就是对的。
- **原理**：串口是**异步**通信 —— 没有时钟线，收发双方只靠约定好的时间长度来采样。波特率不匹配时，接收方在每个位的中间采到错误电平，一个字节被错位解析成两个字节，就出现了 `FFFF` 这种「全 1」的结果。

> 💡 **重要发现**：本项目最初按常见教程写 `9600` 一直乱码，切换为 `38400` 后立即正常 —— 说明这个批次的 HC-05 底板出厂固件默认就是 38400。**不要盲目相信教程里的默认值，以你的实物为准。**

### 2.2 TX/RX 接反 ⭐ 同样常见

| ❌ 接反 | ✅ 正确 |
| --- | --- |
| 蓝牙 TX → D11 | 蓝牙 **TX → D10** |
| 蓝牙 RX → D10 | 蓝牙 **RX → D11** |

- **解决**：**交叉连接**。`SoftwareSerial BT(10, 11)` 中 `10` 是 Arduino 的**接收脚**，所以必须接对方的**发送脚**。
- **症状区分**：

| 症状 | 更可能的原因 |
| --- | --- |
| 有乱码输出 | 波特率不匹配 |
| 完全没有输出 | TX/RX 接反（或没配对） |
| 输出 `D` `A` | 正常，收到的是 `\r\n` |

## 3. 上传代码失败

**现象**：点击上传后报错

```
avrdude: stk500_recv(): programmer is not responding
avrdude: stk500_getsync() attempt 1 of 10: not in sync
```

### 3.1 蓝牙模块干扰下载 ⭐ 本项目特有

`SoftwareSerial` 使用 D10/D11，而这两个引脚在**程序下载和复位阶段**会参与 bootloader 通信流程（作为信号线被拉高/拉低）。HC-05 接在这两根线上，会把下载信号拉偏，导致 bootloader 握手失败。

- **解决**：**每次上传前拔掉 HC-05 的 TX 和 RX 两根线**，上传成功后再插回，并**按一下 Arduino 的 Reset 键**
- **为什么必须按 Reset**？上传完成后 MCU 立即从新程序开始运行，但此时蓝牙线还没插回，`SoftwareSerial` 的初始化可能与模块状态不同步。按 Reset 重新走一遍完整的 `setup()`，链路才干净。
- **进阶方案**：改用 D2/D3 作为软串口（这两个脚是外部中断脚，`SoftwareSerial` 的接收性能更好），或直接换 **Arduino Mega**（有 4 个硬件串口），就能彻底避免这个问题。

### 3.2 开发板或端口选错

- `工具 → 开发板` 必须选 `Arduino Uno`
- `工具 → 端口` 必须选带 `(Arduino Uno)` 字样的那个 COM 口
- 拔插 USB 后 COM 号可能会变，**每次都要重新确认**

### 3.3 USB 线只能充电

市面上大量 Micro-USB 线**只有电源线，没有数据线**（通常随充电宝附赠）。

- **现象**：板子上的电源灯亮，但电脑端口列表里没有串口
- **解决**：换一根确认能传数据的线

### 3.4 串口监视器占用

Arduino IDE 1.8.x 中，串口监视器打开时**会占用串口**，导致上传失败。

- **解决**：上传前关闭串口监视器（IDE 2.x 已自动处理）

## 4. DHT11 频繁报 Sensor Error

**现象**：发送 `T` 时 LCD 显示 `Sensor Error!`，或手机收到 `Sensor Error! Check wiring.`

### 4.1 读取间隔太短

- **解决**：两次 `dht.readTemperature()` 之间**至少间隔 1 秒**（DHT11 的数据手册建议 2 秒以上更稳）
- **原理**：DHT11 是**单总线**传感器，每次测量都需要完整走一遍「主机拉低 → 释放 → 传感器响应 → 传输 40 位数据」的时序。传感器内部需要时间完成一次采样转换，间隔太短会读到上一轮的残留或直接失败。

> ⚠️ **注意**：当前固件是**手机主动查询**模式（发 `T` 才读），不会连续读取。但如果你快速连点发送按钮，仍会触发这个问题。计划中的「5 秒定时上报」会彻底规避。

### 4.2 供电接触不良 ⭐ 面包板高频问题

- **判断依据**：DHT11 模块上的**红色电源指示灯必须常亮**
- **解决**：面包板的孔位用久了会松，把 DHT11 换一排孔位，或直接焊排针用杜邦线连接
- **原理**：DHT11 单总线通信对时序敏感（微秒级），电源电压跌落会导致传感器复位或时序错乱，表现为间歇性读取失败。

### 4.3 线太长 / 干扰

- **解决**：数据线尽量短（< 20cm），远离 LED 的开关走线
- **原理**：单总线是**开漏 + 上拉电阻**结构，抗干扰能力弱。附近的电流突变（LED 开关瞬间）会通过寄生电容耦合到数据线上。

### 4.4 传感器型号选错

```cpp
#define DHTTYPE DHT11   // 如果你用的是 DHT22/AM2302，必须改成 DHT22
```

- **原理**：DHT11 和 DHT22 的**数据格式和温湿度换算公式不同**（DHT11 是整数部分 + 小数部分分离的 8 位格式，DHT22 是完整的 16 位有符号格式）。型号选错会读出完全错误的值，或者直接校验失败。

## 5. LCD 出现残留字符

**现象**：状态从 `OFF` 切到 `ON` 后，屏幕显示 `LED: ONF` —— 多了一个残留的 `F`。

**原因**：LCD1602 是**字符型显示器**，不像图形屏那样有「清像素」的概念。每个字符位置是一个独立的 DDRAM 单元，`print("ON")` 只写了前两个位置，第三个位置仍然是上一次写入的 `F`。

**解决**：在短字符串末尾**刻意补空格**，把残留字符覆盖掉：

```cpp
lcd.print("LED: OFF ");    // 8 个字符
lcd.print("LED: ON  ");    // 同样是 8 个字符（2 个补位空格）
lcd.print("LED: Blink");   // 9 个字符，本身就是最长的，无需补
```

**更彻底的方案**：切换状态前先 `lcd.clear()`，或对整行固定宽度输出：

```cpp
lcd.setCursor(0, 1);
lcd.print("                ");   // 16 个空格清行
lcd.setCursor(0, 1);
lcd.print("LED: ON");
```

> ⚠️ **注意**：`lcd.clear()` 会顺带让光标回到左上角，并且耗时约 2ms。频繁调用会**造成可见的闪烁**。所以本项目的策略是「只在必要时 clear，日常状态刷新靠补空格」。这也解释了为什么 `3`（彩蛋）分支里有 `lcd.clear()` 而普通状态切换里没有。

## 6. 按键不灵敏 / 连击

**现象**：按一下切换了两次状态，或者按下没反应。

**代码里已有的措施：**

```cpp
buttonState = digitalRead(buttonPin);
if (buttonState == LOW && lastButtonState == HIGH) {   // 边沿检测：只在"按下瞬间"触发
  ...
  delay(150);                                          // 软件消抖
}
lastButtonState = buttonState;
```

**如果仍然有问题：**

| 原因 | 解决 |
| --- | --- |
| 按键接触不良（廉价轻触开关常见） | 换一个按键 |
| 面包板孔位松 | 换孔位 |
| 机械抖动超过 150ms | 把 `delay(150)` 增到 `200` |
| 硬件干扰 | 按键两端并联 **0.1µF 电容** 做硬件消抖 |

**原理**：机械按键在按下和释放的瞬间，金属触点会弹跳多次（持续约 5~20ms），MCU 会读到一个 `LOW-HIGH-LOW-HIGH` 的抖动序列。软件延时消抖是「等抖动过去再读」，硬件电容消抖是「用电容把抖动滤掉」。

> 💡 **改进方向**：`delay(150)` 本身是**阻塞**的，虽然只有 150ms 影响不大，但与项目「非阻塞」的设计理念不一致。更好的写法是用 `millis()` 做消抖时间戳：

```cpp
if (buttonState == LOW && lastButtonState == HIGH && millis() - lastDebounceTime > 150) {
  lastDebounceTime = millis();
  // 切换状态
}
```

## 7. LED 不亮或很快烧毁

### 7.1 不亮

- **极性接反**：LED 长脚是阳极（+）接 GPIO，短脚是阴极（−）接 GND
- **没加限流电阻**导致已烧毁：用万用表二极管档测一下，好的 LED 会微亮
- **引脚号写错**：本项目最终版是 D9 和 D8，早期 `led_running_on_off` 用的是 D5

### 7.2 烧毁 ⚠️ 必须避免

**绝对不要把 LED 直接跨接在 GPIO 和 GND 之间。**

- ATmega328P 单个 IO 口的安全输出电流上限约 **20mA**（绝对最大值 40mA）
- 一颗没有限流电阻的红色 LED，正向压降约 1.8V，从 5V 引脚取电时电流可达 **100mA 以上**
- 后果：LED 烧毁 → 严重时**永久损伤 IO 口**（该脚输出能力下降或失效）

**限流电阻选型表（5V 供电）：**

| 电阻 | 电流（红色 LED，Vf≈1.8V） | 效果 |
| --- | --- | --- |
| 100Ω | ~32mA | ⚠️ 超过 IO 安全值，不推荐 |
| **220Ω** | **~15mA** | ✅ 本项目使用，亮度充足且安全 |
| 330Ω | ~10mA | ✅ 更保守 |
| 1kΩ | ~3mA | 很暗，仅适合指示 |

**计算公式：**

```
R = (Vcc − Vf) / I = (5V − 1.8V) / 0.015A ≈ 213Ω  →  取标称值 220Ω
```

## 8. 电脑识别不到串口

| 检查项 | 说明 |
| --- | --- |
| USB 线是否支持数据 | ⭐ 最常见原因，换线试试 |
| 是否装了 CH340 驱动 | 国产兼容板多用 CH340/CH341 芯片，**必须手动装驱动**（原版 Uno 用 ATmega16U2，免驱） |
| 设备管理器有无异常 | 出现黄色感叹号 → 驱动问题 |
| 换 USB 口 | 前面板 USB 口供电可能不足，试机箱后面板 |
| 板子是否短路 | 拔掉所有外设只留 USB，看能否识别 |

**CH340 驱动**：[WCH 官网](http://www.wch.cn/downloads/CH341SER_EXE.html) 下载安装后重新插拔即可。

## 9. 蓝牙连不上 / 配对后立刻断开

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 搜不到 `HC-05` | 模块未供电 | 检查 VCC/GND，底板 LED 应快闪 |
| 搜索到但配对失败 | 配对码错误 | 试 `1234` 和 `0000` |
| 配对成功但连不上 | App 选了 BLE 模式 | 经典蓝牙要用 SPP 模式，别选 BLE 扫描 |
| 连上后立刻断开 | 供电不足 | HC-05 配对/发射瞬间电流可达 40mA+，从 Arduino 5V 直取，必要时并联 100µF 电容 |
| 连接后 LED 不慢闪 | 未真正建立链路 | 重新配对 |
| 距离很短 | 天线被遮挡 | ⚠️ 模块顶部的**波浪形天线区域不要贴近金属或面包板电源轨** |

**LED 指示含义：**

- **快闪**（约 1 秒 2 次）：未连接，可被搜索/配对
- **慢闪**（约 2 秒 1 次）：已连接，可以收发数据
- **常亮**：AT 命令模式（KEY 引脚接高电平时）

## 10. 闪烁时蓝牙指令丢失

**现象**（改编自常见写法）：用 `delay()` 写闪烁，闪烁期间手机发的指令全部丢失，LED 也不响应按键。

**原因**：`delay(200)` 会让 MCU **完全停止执行** 200ms。在这期间：

- 蓝牙模块收到的字节堆在 Arduino 的 64 字节软串口缓冲区里
- 如果连发多条指令，缓冲区**溢出**，字节被静默丢弃
- 按键扫描也停了，按下无响应

**解决**：改用 `millis()` 时间戳（本项目采用）：

```cpp
unsigned long previousMillis = 0;
const long blinkInterval = 200;

if (ledMode == 2) {
  unsigned long currentMillis = millis();
  if (currentMillis - previousMillis >= blinkInterval) {
    previousMillis = currentMillis;
    blinkState = !blinkState;
    digitalWrite(ledPin1, blinkState ? HIGH : LOW);
    digitalWrite(ledPin2, blinkState ? LOW : HIGH);
  }
}
```

`loop()` 依然以微秒级速度不断轮询，**闪烁、蓝牙、按键、串口全部并行工作**。

> 💡 **为什么 `currentMillis - previousMillis` 是安全的？**
> `millis()` 返回 `unsigned long`，约 49.7 天溢出一次。用**无符号减法**时，即使发生溢出，`currentMillis - previousMillis` 的结果仍然正确（这是模 2³² 运算的性质）。**不要**写成 `if (currentMillis > previousMillis + interval)` 或 `if (millis() % interval == 0)`，前者在溢出时会失效，后者会因 `loop()` 执行速度而产生重复触发或漏触发。

## 11. `screen_words.ino` 文件损坏事件

**现象**：[firmware/screen_words/screen_words.ino](../firmware/screen_words/screen_words.ino) 文件第一行是一长串无意义的 `AAAA...QQQQ...` 字符，代码从第 2 行才开始。

**真实原因**：开发早期，串口监视器里曾因为**波特率不匹配**打印出大量乱码；在复制/粘贴或串口数据重定向的过程中，这段乱码被误写进了源文件的开头。

**影响**：文件无法编译（第一行是语法错误）。

**处理方式**：**原样保留**。理由有三：

1. 它是这个项目真实开发轨迹的一部分，抹掉就丢掉了「踩坑证据」
2. 它直观地展示了波特率不匹配会造成什么后果
3. 去掉第一行后代码完全可用，需要时自己删掉即可

**正确的代码内容**（去掉损坏行后）：

```cpp
// 引入 LiquidCrystal 库
#include <LiquidCrystal.h>

// 初始化引脚顺序：RS, E, D4, D5, D6, D7
LiquidCrystal lcd(12, 11, 5, 4, 3, 2);

void setup() {
  lcd.begin(16, 2);
  lcd.print("Hello, TEST");
  lcd.setCursor(0, 1);
  lcd.print("Arduino LCD Test");
}

void loop() {
  for (int thisChar = 0; thisChar < 10; thisChar++) {
    lcd.setCursor(14, 1);
    lcd.print(thisChar);
    delay(500);
  }
}
```

## 🧰 通用排错流程

遇到问题时按这个顺序走，能覆盖 90% 的情况：

```
1. 看指示灯
   ├─ Arduino 电源灯亮？         → 否则查 USB 线和供电
   ├─ LCD 背光亮？               → 否则查 I2C 的 GND/VCC
   ├─ DHT11 红灯亮？             → 否则查面包板接触
   └─ HC-05 快闪/慢闪？          → 快闪=未连接，慢闪=已连接

2. 看串口输出（9600 波特率）
   ├─ 完全没有输出               → 程序没跑起来 / 端口选错
   ├─ 有输出但乱码               → 波特率不匹配
   └─ "BT Received (HEX): 31"   → 通信链路完全正常 ✅

3. 分段验证
   ├─ 只跑 LCD 代码，能显示吗？
   ├─ 只跑蓝牙代码，能收字符吗？
   ├─ 只跑 DHT 代码，能读数吗？
   └─ 逐个通过后再合并 → 快速定位是哪个模块的问题

4. 检查接线（用万用表通断档）
   └─ 面包板孔位是最大嫌疑犯
```

### 三个「万能」检查

| 检查 | 命令 / 方法 |
| --- | --- |
| I2C 设备在不在 | 跑 i2c_scanner，看是否输出 `0x27` |
| 蓝牙收得到吗 | 看串口是否打印 `BT Received (HEX): 31` |
| 传感器活着吗 | 单独跑 `文件 → 示例 → DHT sensor library → DHTtester` |
